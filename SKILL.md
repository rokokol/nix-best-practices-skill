# nix-best-practices

Nix has a formatter that settles layout and two linters that settle the language's own antipatterns. What is left over is everything they cannot see: the scope an expression opens, where an option is declared against where it is read, whether a package says what it is, whether a lock describes a machine instead of a project. That residue is what this standard is, and the test for whether a line belongs in it is whether a tool already decides it

The second thing they cannot see is time. A derivation's hash, an input's copy, an option's path: each is correct on the machine that wrote it and wrong on the next one, or correct today and wrong after a rename upstream. Most of the rules below are about that gap rather than about taste

[`check-nix.sh`](check-nix.sh) beside this file is the mechanical half. It runs the three tools and adds what none of them reach, and on every run it plants one defect per check into fixtures it prints itself and requires each to be rejected for that defect's own reason

## Doing the work

- **Start a new file from `./check-nix.sh --template module`**, or `package`, or `flake` — each is the shape below already assembled, and each is what the checker proves itself against
- **End every change with `./check-nix.sh`**, from the repository root or with `-C DIR`; a repository that wires the checker into its `checks` output gets the same rules from `nix flake check`, minus the two that need the flake's inputs
- **Ask `./check-nix.sh --list-rules` what it holds a tree to**, and `--help` for what each flag does, rather than inferring either from a finding
- **Read a finding as a question about the code, not about the checker** — but when the answer is that this repository is the exception, say so once in `check-nix.allow` rather than in every review
- **After a change meant to leave behaviour alone, ask `./drv-diff.sh` whether it did.** It evaluates every output of the flake here and at another revision and names the ones whose derivation path moved. Naming one output by hand answers a narrower question: what moves is rarely the output anybody thought to name, and a derivation that turns out to depend on the whole repository is found the same way

## The core

- **The formatter owns layout, so nothing here describes layout.** Indentation, line breaks, where a list wraps, what becomes of a block comment: `nixfmt` decides all of it, and a repository declares it as `formatter` so that one command settles the question everywhere. What the formatter keeps either way — the order of a module's arguments, whether two share a line and three are stacked — is on the author, and that is the only part written down. See [references/format.md](references/format.md)
- **`with` opens a scope, and the scope is one expression whose body binds nothing of its own.** A package list, a `meta`, a type: the body is visible whole and there is nothing inside it for the scope to collide with. Over a file or over a `let` it loses to every name bound later, silently and regardless of the order they are written in, because `with` sits below both in the lookup. The short form that keeps the brevity is `inherit (lib) mkIf mkOption types;`, which declares its names instead of offering them. See [references/scope.md](references/scope.md)
- **An option is declared in the module that acts on it, and the module gates itself.** `config = lib.mkIf cfg.enable { … }` rather than another module reaching for `config.services.foo.enable`; a `default.nix` that only imports, so the file that aggregates is never also the file that configures. Which layer a thing belongs to — system or user — is decided by what it touches, not by which file was open. See [references/modules.md](references/modules.md)
- **A flake input is named once and followed, an output is declared, and the lock describes the project rather than a machine.** An input that brings its own copy of something shared makes two of it, and the two drift without a word. A `path:` that points at a home directory travels into the lock through an ordinary commit and then fails everywhere but there — and not on the machine that wrote it, which already holds the content. See [references/flakes.md](references/flakes.md)
- **A derivation says what it is, who may use it and where it runs, and its source is isolated from the repository around it.** `meta` in the grammar nixpkgs asks for, because that grammar is what every tool reading a package expects; a `src` taken straight from `inputs.self` ties the hash to every commit in the repository and rebuilds on each. When the question is what a package actually is, ask the built derivation rather than the expression that produced it. See [references/packages.md](references/packages.md)
- **Prefer the form that evaluates the same on any machine.** A lookup path reads `$NIX_PATH`, a channel reads what was last added, `builtins.getEnv` reads the environment: each turns a flake into a description of one computer. `pkgs.lib` beside a `lib` argument is the same shape in miniature — two names for one thing, and only one of them is pinned by the module system. See [references/language.md](references/language.md)
- **A comment carries what the code cannot.** A module's file comment sits after the argument header and against the body, so it is met with the code it explains; attribution for vendored work sits above the header, where a licence header goes. A comment inside a list or an attrset also stops the formatter collapsing it, which makes its placement a question about the diff and not only about reading. See [references/comments.md](references/comments.md)
- **Three tools decide what they can, from the lock rather than from the network.** `nixfmt` for layout, `statix` for the language's antipatterns, `deadnix` for what nothing reads; two statix lints are off everywhere because they argue with the module system rather than with the code. In a check they come from the repository's own devShell, never from a registry lookup that can answer differently tomorrow. See [references/lint.md](references/lint.md)

Following the letter of a rule while breaking its point is breaking the rule; the rules are short so the point can be read. The manuals, standards and measurements these rest on are listed in [references/sources.md](references/sources.md)
